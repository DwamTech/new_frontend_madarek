# مدارك — النسخة الجديدة

إعادة بناء الواجهة الأمامية لمجلة مدارك (mdarek.net) بـ Next.js، مع الإبقاء على نظام الإدارة والبيانات القديم (back.mdarek.net) كما هو دون أي تعديل عليه.

## الفكرة المعمارية باختصار

الموقع لا يملك قاعدة بيانات خاصة به. كل المحتوى (الأعداد، المقالات، الكتّاب) يأتي وقت البناء/الطلب من الـ API العام للنظام القديم:

```
back.mdarek.net/api  →  src/lib/mdarek-api/  →  الصفحات (src/app)
```

طبقة `src/lib/mdarek-api/` هي الحد الفاصل الوحيد الذي يعرف شكل بيانات النظام القديم:

| ملف | دوره |
|---|---|
| `env.ts` | متغيرات البيئة (عنوان الـ API، المهلة، مدة الكاش) |
| `client.ts` | نداء fetch بمهلة وكاش موحّدين |
| `raw-types.ts` | شكل استجابات الـ API **كما هي فعليًا** — مرجع دقيق لأي مبرمج باكند |
| `adapter.ts` | يحوّل الشكل الخام إلى نماذج داخلية نظيفة (`types.ts`) — يعزل بقية الموقع عن غرابات النظام القديم |
| `sanitize.ts` | تنظيف HTML القادم من المحرر القديم قبل عرضه |
| `index.ts` | دوال الجلب النهائية التي تستوردها الصفحات، بالكاش (ISR) |

أي صفحة في `src/app` **لا تستدعي الـ API مباشرة أبدًا** — فقط عبر دوال `src/lib/mdarek-api/index.ts`.

## التشغيل محليًا

```bash
npm install
cp .env.example .env.local   # ثم تحقق من القيم
npm run dev
```

الموقع على `http://localhost:3000`.

### متغيرات البيئة (`.env.local`)

انظر `.env.example` — الأهم:
- `MDAREK_API_BASE`: عنوان الـ API القديم (قراءة فقط، بلا مفاتيح، بلا صلاحيات).
- `MDAREK_API_REVALIDATE_S`: مدة صلاحية الكاش بالثواني قبل إعادة الجلب (افتراضيًا 1800 = 30 دقيقة). النظام القديم نفسه بلا كاش خاص به (تحقّق ميداني)، فتقصير هذه المدة يُظهر أي تعديل تحريري أسرع دون كلفة إضافية.

## أوامر مفيدة

```bash
npm run dev      # تشغيل محلي مع Turbopack
npm run build    # بناء الإنتاج
npm run lint     # فحص ESLint
npm run test     # اختبارات Vitest (تُشغَّل على fixtures، بلا اتصال شبكة حقيقي)
```

قبل أي commit يجب أن تمر الأربعة السابقة بلا أخطاء، إضافة إلى `tsc --noEmit`.

## البنية

```
src/app/            الصفحات (App Router)
src/components/     مكوّنات واجهة مشتركة
src/lib/mdarek-api/ طبقة الاتصال بالنظام القديم (التفصيل أعلاه)
src/lib/            أدوات مساعدة عامة (تنسيق، ألوان الأبواب...)
docs/backend-requests/          طلبات تعديل/إضافة حقول معلّقة على فريق الباكند
```

## طلبات معلّقة على الباكند

راجع [`docs/backend-requests/`](./docs/backend-requests) — كل طلب فيه موثَّق بصيغة: السياق، التعديل المطلوب، لماذا لا تكفي الحقول الحالية، وأثر التعديل. إضافة أي حقل جديد للـ API **لا تكسر شيئًا** في هذا الموقع — طبقة `adapter.ts` تتجاهل أي حقل غير معروف لها.

## النشر

الموقع منشور على Vercel، ومربوط مباشرة بهذا المستودع (Git Integration): أي `push` إلى فرع `master` يُطلق بناءً ونشرًا تلقائيًا على الإنتاج، بلا أي أمر يدوي.

يتطلب متغيرات البيئة نفسها معرَّفة في إعدادات مشروع Vercel (وليس فقط `.env.local` المحلي).

## ملاحظة عن هذا الملف نفسه

هذا `README.md` كُتب خصيصًا لهذا المشروع — الملف الافتراضي من `create-next-app` استُبدل بالكامل لأنه لم يكن يشرح شيئًا عن آلية الاتصال بالبيانات الحقيقية، وهو أول ما يحتاجه أي مطوّر جديد ينضم للمشروع.
